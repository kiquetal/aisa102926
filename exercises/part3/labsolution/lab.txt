# Recommended Architecture: Tax Filing Platform

**Short answer:** a **modular, service-oriented architecture** (a "modular monolith" at the core, with a few independently deployed services where the characteristics demand it), built on an **event-driven backbone**, with a **rules engine** for tax logic and an **anti-corruption/adapter layer** for every external authority. I would not start with a full microservices mesh.

## 1. Why this style

| Driver | Architectural consequence |
|---|---|
| Security, privacy, compliance (bank data, SSNs, payments) | Isolate sensitive data and payment handling into small, hardened services; minimize PCI/PII scope |
| Correctness, auditability, traceability | Tax calculation as a deterministic, versioned rules engine; append-only audit/event log |
| Interoperability | Adapter (ports and adapters) layer per authority: IRS MeF, each state's e-file system |
| Availability, scalability, resilience | Stateless services, queues, and autoscaling to survive the January-April spike and authority outages |
| Upgradability, maintainability | Tax law changes every year, so rules are data/config versioned by tax year, not hard-coded |
| Localization, accessibility, usability | Thin client layer with i18n (en/es) and WCAG 2.2 AA, with all content externalized |

Tax software has an extreme seasonal load profile and a hard annual change cycle. A modular monolith with a few extracted services gives you clear boundaries without the operational burden of 30 microservices, and the boundaries let you split later.

## 3. Key components and decisions

**Tax Rules Engine (the heart of correctness)**
- Pure, deterministic calculation library: same inputs plus the same rule version produces the same output, always.
- Rules are versioned per **tax year and jurisdiction** (federal plus 50 states, with local taxes where relevant). Prefer a declarative rules/DSL model (e.g., a dependency graph of form lines like the IRS's own forms) so tax analysts can update it without full redeploys.
- Multi-state support: a "residency and income allocation" module that apportions income across states (part-year/non-resident returns, credit for taxes paid to other states), feeding one calculation per state.
- Heavy automated testing: golden-file tests against IRS/state test scenarios, property-based tests, and regression suites per tax year.

**Household and filing-status model**
- Model **Person**, **Household**, and **Return** as separate entities; a *Return* has a filing status (single, MFJ, MFS, HoH, dependent) and a set of *participants* with roles and permissions.
- Delegation model (preparer-for-family, spouse co-signing) uses fine-grained authorization (ReBAC/ABAC, e.g., Zanzibar-style or OPA policies), because "user files for several family members" is really a permissions problem.

**Filing Orchestration (resilience and interoperability)**
- A **saga/workflow engine** (e.g., Temporal or a state-machine on a queue) drives: validate → sign/consent → transmit → await acknowledgment → accepted/rejected → handle reject/resubmit.
- Each authority gets an **adapter** behind a common port interface, translating the internal canonical return into IRS MeF XML schemas or each state's format. Adapters handle schema versions, certificates, and quirks, so one state's change never ripples through the core.
- Idempotency keys, retries with backoff, circuit breakers, and a dead-letter queue. Authority downtime is normal; the user sees "queued" instead of an error.
- Federal and state submissions are tracked independently, since states may accept or reject separately.
- Consider whether to be an **Authorized IRS e-file Provider** (required to transmit); this drives compliance requirements (see below).

**Data Vault and security**
- Segregate **sensitive data** (SSN, bank routing/account numbers, ID documents) into a dedicated vault service with envelope encryption (per-tenant/per-user data keys in KMS/HSM), strict access paths, field-level encryption, and tokenization. Other services hold tokens, not raw values.
- TLS everywhere and mTLS between services, secrets management, WAF, DDoS protection, MFA (phishing-resistant options like passkeys), and anomaly/fraud detection (tax identity theft is a major threat).
- Data residency in US regions, backups encrypted, and retention/deletion policies aligned with legal retention rules.

**Billing and Payments**
- Use a **PCI-compliant payment provider with hosted fields/checkout** so card data never touches your systems (keeps you at SAQ-A scope).
- Support "pay from refund" only through the proper financial-product channels if you offer it (requires bank partnerships).

**Notifications**
- Event-driven: status events (submitted, accepted, rejected) flow to a notification service that renders localized templates (en/es) and sends via email/SMS/push providers, with user preferences, opt-outs, and delivery tracking. Keep messages free of sensitive data ("your status changed, log in to view").

**Audit and traceability**
- **Event sourcing (or at least an append-only, tamper-evident audit log)** for return changes, consents, e-signatures, submissions, and acknowledgments. Every submitted figure should trace to its source input, rule version, and user action.
- Immutable storage (WORM) for submitted-return snapshots and authority acknowledgments.

## 4. Deployment and operational view

- **Cloud-native**, multi-AZ (ideally multi-region active-passive) on Kubernetes or a managed container platform; stateless services with horizontal autoscaling and **pre-scaling before filing season** and the deadline spikes (mid-April and extension deadlines).
- **Databases:** relational (PostgreSQL) for transactional/return data with strong consistency, because correctness matters more than raw scale here. Object storage for documents. Cache/queue layer for load smoothing.
- Queue-based load leveling to absorb the deadline surge without dropping requests.
- Define SLOs and RPO/RTO targets, with tested disaster recovery and chaos/failure drills before season.
- **CI/CD** with infrastructure as code, blue/green or canary deployments, feature flags, and a **change freeze** during peak season. Separate pipelines for rule updates versus code releases.
- Observability: distributed tracing with correlation IDs (also supports traceability), metrics, centralized logs with PII scrubbing.

## 5. Localization, accessibility, usability

- Externalized strings and content (ICU message format), with **tax terminology reviewed by qualified translators**, since Spanish tax terms must be legally and semantically precise. Locale-aware formatting, plus language switching mid-flow.
- Interview-style guided UX (one question at a time), autosave, clear error messages, undo, and "explain this" help to support error tolerance and usability.
- WCAG 2.2 AA, screen reader and keyboard support, and plain language; test with assistive tech.
- Design the UI as a shared component library driven by a **form/interview definition schema** so the question flow comes from the same versioned configuration as the rules.

## 6. Compliance considerations to drive requirements early

- **IRS:** Publication 1345 and e-file provider rules (EFIN, ATS testing and annual MeF schema updates), **IRC §7216** (consent for use/disclosure of tax return information), and the FTC Safeguards Rule / **IRS Pub. 4557** security-plan requirements (written information security program).
- **Privacy:** state laws (CCPA/CPRA, others), GLBA, and clear consent management.
- **Payments:** PCI DSS. **Banking data:** NACHA rules if you handle ACH.
- **Accessibility:** ADA/Section 508 expectations.
- Security assurance: SOC 2 Type II, regular penetration tests, and threat modeling (STRIDE) per service.

## 7. Trade-offs and alternatives

- **Full microservices from day one:** better independent scaling and team autonomy, but heavy operational complexity and distributed-consistency risk for a calculation-centric domain. Better as an evolution once boundaries stabilize.
- **Pure monolith:** simplest, but weak isolation for sensitive data and payments, and harder to scale the filing/transmission path independently.
- **Event sourcing everywhere:** excellent auditability, but added complexity; I'd apply it to the Return and Filing aggregates and use plain CRUD with audit logging elsewhere.
- **Build vs. buy:** consider licensing or partnering for the tax calculation engine and state form libraries (e.g., commercial tax content providers) and for transmission, since maintaining 50-state content is the largest ongoing cost.

## 8. Mapping characteristics to tactics

| Characteristic | Primary tactics |
|---|---|
| Security / Privacy | Vault, field encryption, tokenization, least privilege, MFA, fraud detection |
| Correctness / Data integrity | Deterministic versioned rules engine, golden tests, ACID DB, checksums, validation before transmit |
| Interoperability | Adapter layer, canonical return model, schema versioning |
| Availability / Resilience | Multi-AZ/region, queues, retries, circuit breakers, graceful degradation |
| Scalability | Stateless services, autoscaling, queue-based load leveling, pre-scaling |
| Upgradability / Maintainability | Modular boundaries, rules as versioned data, CI/CD, feature flags |
| Accessibility / Localization / Usability | WCAG 2.2, i18n framework, guided interview UX |
| Compliance / Auditability / Traceability | Append-only audit log, event sourcing for returns, WORM storage, correlation IDs |
| Error tolerance | Autosave, validation with clear messaging, idempotent operations, reject/resubmit workflow |

## Recommended: modular monolith on managed services

**Shape:** one codebase and one deployable, split internally into modules with strict boundaries (Identity, Household, Return Preparation, Tax Rules, Filing, Billing, Notifications, Audit). Modules talk through defined interfaces, never by reaching into each other's tables. A second process type from the same codebase runs background workers for transmission and notifications.

```
 Web/PWA (en/es)  ──►  Single app (load-balanced, stateless, 2+ instances)
                        ├─ Identity  ├─ Household  ├─ Return Prep
                        ├─ Tax Rules (library) ├─ Filing  ├─ Billing
                        ├─ Notifications  └─ Audit
                                   │
                  Worker process (same code): transmit, poll status, send notices
                                   │
   Managed PostgreSQL (schema per module) │ Object storage │ Managed job queue
   KMS (field encryption) │ Hosted payments │ Managed email/SMS │ Managed auth
```

## What you keep from the earlier design (these are cheap)

- **Tax rules as a versioned, deterministic library** by tax year and jurisdiction. This is the core of correctness and upgradability, and it needs no extra infrastructure.
- **Adapter layer per authority** (IRS plus each state) behind one interface. This is just code structure, but it isolates interoperability pain.
- **Append-only audit table** plus correlation IDs in logs for auditability and traceability. Skip full event sourcing.
- **Outbox pattern plus a queue** for transmission and notifications, so authority outages become "queued," not errors, with retries and idempotency keys.
- **Field-level encryption with KMS** for SSN and bank data, implemented as a module with a narrow API instead of a separate vault service.
- **i18n and WCAG** in the front end, which cost the same under any architecture.

## What you drop

- Separate services, API gateway, service-to-service mTLS, and a message broker cluster
- Kubernetes (use a PaaS or managed containers such as App Runner, Cloud Run, or Fargate)
- Event sourcing everywhere, multi-region active-active, and a separate workflow engine (a simple state machine in the DB is enough to start)

## Biggest cost levers (beyond architecture style)

1. **Buy or license the tax calculation content and transmission.** Maintaining 50-state rules and annual IRS MeF schema changes is usually the largest ongoing cost. Commercial tax engines and transmitter APIs can replace most of the Tax Rules and Adapter work.
2. **Never touch card data.** Use hosted checkout from a PCI-compliant provider.
3. **Use managed auth, database, email/SMS, and secrets.** You pay a bit more per unit, but you avoid the operations staff.

## How the characteristics are still met

| Characteristic | How, at lower cost |
|---|---|
| Security/privacy | Field encryption via KMS, MFA, WAF, least-privilege DB roles, hosted payments |
| Correctness/integrity | Versioned rules library, ACID Postgres, validation before transmit, golden-file tests |
| Availability/resilience | Multi-AZ managed DB, 2+ stateless instances, queue with retries |
| Scalability | Horizontal app and worker scaling, pre-scale for January to April and the deadline spikes |
| Auditability/traceability | Audit table, immutable snapshots of submitted returns in object storage |
| Maintainability/upgradability | Module boundaries enforced by tests or lint rules, rules versioned per year |

## Trade-offs to accept

- The whole app deploys together, so a bad release affects everything. Mitigate with CI tests, canary or blue/green deploys, and a change freeze in peak season.
- Scaling is coarser, though the worker process can scale independently, which covers the main hot spot.
- Compliance scope is broader for the app. IRS Pub. 4557, GLBA, and SOC 2 apply regardless, but hosted payments and KMS keep it manageable.

## When to split later

Extract a module into its own service only when there is a concrete reason: the transmission/adapters component needs separate scaling or its own security boundary, a team needs independent release cadence, or auditors want sensitive-data handling isolated. The enforced module boundaries make that a refactor, not a rewrite.

How about a microkernel architecture? Is that something to consider as well as it is also quite modular?



Yes, it is worth considering, but as a pattern **inside** the modular monolith rather than as a replacement for it. The two are compatible, and combining them fits your domain well.

## Where microkernel fits: the jurisdiction layer

A microkernel keeps a small, stable core and pushes variable behavior into plug-ins. Your system has one obvious axis of variation: **federal + 50 states, each changing every tax year**, each with its own rules, forms, interview questions, and e-file format. That is a textbook plug-in problem.

```
                 Core (the "kernel")
   Identity │ Household │ Return lifecycle │ Calc orchestration
   Validation runner │ Filing workflow │ Billing │ Audit │ Notifications
                          │
              Plug-in contract (interface)
      ┌──────────┬──────────┬──────────┬──────────┐
   Federal     CA         NY         TX   ...  (each versioned by tax year)
   2026        2026       2026       2026
   rules, forms, interview questions, validations,
   e-file mapping/adapter, en/es strings
```

Each jurisdiction plug-in implements the same contract, for example: declare required inputs, calculate, validate, produce the submission payload, and parse the acknowledgment or rejection. The core never contains state-specific logic.

## What you gain

- **Adding or updating a state doesn't touch the core.** You ship a new plug-in or a new year's version.
- **Multi-state filing becomes natural.** The core loads the plug-ins for each state the user earned in and runs them in order.
- **Isolated testing.** Each plug-in has its own golden-file suite per year.
- **Fits your characteristics:** upgradability, maintainability, interoperability, localization (strings travel with the plug-in), and traceability (every figure is tagged with the plug-in and version that produced it).
- **No extra infrastructure.** Plug-ins are normally in-process, so there is no cost penalty like SOA's.

## Where it doesn't fit

The rest of the system (identity, household, billing, notifications, audit) is not variable. It is a fixed set of capabilities with a fixed workflow, so a plug-in model adds indirection without benefit. Those belong as ordinary modules.

## Risks to manage

1. **Jurisdictions are not independent.** State returns often start from federal AGI, and multi-state filers claim credits for taxes paid to other states. You need an explicit dependency model, for example federal outputs published as a typed data set that state plug-ins consume, plus an ordering or dependency graph for calculation. Skipping this is the most common way plug-in designs break down.
2. **The plug-in contract is hard to get right.** If it is too narrow, you will keep changing the core. Prototype it with the federal plug-in plus two structurally different states (say, one with no income tax and one with a complex part-year/non-resident return) before committing.
3. **Version matrix.** You will have combinations of core version, tax year, and plug-in version. Keep the contract versioned and the plug-ins pinned to it.
4. **Don't over-engineer loading.** Compile-time registration of plug-ins is enough. Dynamic loading, hot-swapping, or third-party sandboxing is unnecessary unless you plan an external plug-in marketplace.
5. **Sensitive data.** Plug-ins should receive only the fields they need through the contract, and never access the vault or database directly.

## Recommendation

| Level | Style |
|---|---|
| Overall system | Modular monolith (as in my previous answer) |
| Tax rules, forms, and authority adapters | Microkernel/plug-in pattern, one plug-in per jurisdiction per tax year |
| Everything else | Plain modules with enforced boundaries |

This gives you the lowest-complexity deployment while concentrating flexibility where tax law actually changes. It also pairs well with the buy-vs-build option: a licensed commercial tax engine for some or all states can simply be wrapped as a plug-in behind the same contract.
